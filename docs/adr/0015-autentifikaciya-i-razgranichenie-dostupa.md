# ADR-0015. Аутентификация и разграничение прав доступа

- **Статус:** принято
- **Дата:** 2026-09-26

## Контекст

До настоящего этапа программный интерфейс был доступен без проверки
подлинности. Для системы, содержащей сведения о составе инвестиционных
портфелей и результатах оценки риска, такое положение недопустимо:
состав портфеля и величина принимаемого риска составляют коммерческую
тайну организации.

Требовалось определить, **что именно** разграничивается. Рассматривались
две модели.

**Модель обособленных пользователей.** Каждый пользователь видит только
собственные портфели. Такая модель принята в приложениях для частных
инвесторов.

**Модель ролей в организации.** Пользователи принадлежат одной
организации, работают с общим справочником инструментов и общей историей
котировок, но обладают различными полномочиями.

Принята вторая модель. Основание: система предназначена для подразделения,
управляющего риском, а не для частного инвестора. Руководитель обязан
видеть риск по всем портфелям организации — именно совокупный риск, а не
риск закреплённых за отдельным сотрудником позиций, подлежит управлению.
Обособление портфелей по пользователям сделало бы невозможным выполнение
основной задачи системы.

## Решение: три роли

| Роль | Полномочия |
| --- | --- |
| Наблюдатель | Ознакомление со всеми портфелями, результатами расчётов и отчётами без права изменения данных |
| Аналитик | Полномочия наблюдателя, а также ведение собственных портфелей, выполнение расчётов по любым портфелям, формирование отчётов |
| Администратор | Полномочия аналитика, а также ведение справочника инструментов, загрузка данных из внешних источников, управление учётными записями, просмотр журнала действий |

Роли соответствуют разделению обязанностей, принятому в подразделениях
управления риском: ведение справочника инструментов и загрузка рыночных
данных относятся к сопровождению системы, а не к аналитической работе.
Ошибка в справочнике искажает результаты расчётов по всем портфелям
одновременно, поэтому право его изменения предоставляется ограниченному
кругу лиц.

Выполнение расчёта **не** отнесено к изменяющим действиям: расчёт не
изменяет исходных данных, а его результат воспроизводим. Аналитик вправе
рассчитать риск по любому портфелю организации.

## Решение: разграничение на двух уровнях

Разграничение доступа выполняется на двух различных уровнях, и различие
между ними существенно.

**Принадлежность к роли** проверяется до выполнения метода — средствами
политик доступа ASP.NET Core. Такая проверка не требует обращения к базе
данных: роли содержатся в маркере доступа.

**Принадлежность объекта пользователю** может быть установлена только
после обращения к базе данных, то есть внутри службы слоя приложения.
Правило: изменять состав портфеля вправе создавший его пользователь
и администратор.

Службы слоя приложения не зависят от веб-приложения и не могут
формировать ответ протокола самостоятельно. Они сообщают об отказе
исключением `AccessDeniedException`, которое перехватчик
`AccessDeniedExceptionFilter` переводит в состояние 403. Перехватчик
зарегистрирован глобально: отказ обрабатывается единообразно и не требует
повторения обработки в каждом методе контроллера.

Портфель, владелец которого не установлен, считается общим и доступен для
изменения любому аналитику. Такие портфели возникают при переходе
с версии системы, не содержавшей подсистемы удостоверения личности:
столбец `owner_user_id` допускает неопределённое значение, и записи,
созданные ранее, его не содержат.

## Решение: требование подлинности по умолчанию

Требование подлинности применяется ко всем методам программного
интерфейса глобальным фильтром. Исключения обозначаются явно признаком
`AllowAnonymous`: их два — вход в систему и проверка работоспособности
`/health`.

Основание: противоположный порядок, при котором защита назначается
каждому методу в отдельности, приводит к тому, что вновь добавленный
метод остаётся незащищённым по недосмотру. Принятый порядок делает
незащищённость следствием явного решения, а не упущения.

## Решение: маркер доступа вместо состояния сеанса

Применяется схема с маркером в формате JWT, подписанным алгоритмом
HMAC-SHA256.

Основание: клиентское приложение выполняется в браузере и представляет
собой отдельно размещаемое приложение. Проверка подлинности, опирающаяся
на состояние сеанса на стороне сервера, потребовала бы хранения этого
состояния и его согласования при размещении нескольких экземпляров
приложения. Маркер проверяется по подписи без обращения к базе данных.

Отрицательная сторона решения существенна и должна быть названа:
**маркер невозможно отозвать до истечения срока его действия**. Перевод
учётной записи в недействующие предотвращает последующие входы, но
не прекращает действия уже выпущенного маркера. Срок действия маркера
ограничен двенадцатью часами — величина выбрана как соответствующая
продолжительности рабочего дня: она избавляет пользователя от повторного
входа в течение дня и ограничивает последствия утраты маркера.

В маркер помещаются идентификатор пользователя, имя пользователя, фамилия
с инициалами, должность и перечень ролей. Маркер подписан, но
**не зашифрован**: помещать в него сведения, составляющие тайну,
недопустимо. Перечисленные сведения таковыми не являются и требуются
клиентскому приложению для построения интерфейса.

## Решение: ключи и пароли вне репозитория

Репозиторий является общедоступным. Ключ подписи маркеров
(`Jwt:SigningKey`) и пароль учётной записи администратора, создаваемой при
первом запуске (`Seed:AdministratorPassword`), хранятся в хранилище
секретов среды разработки и в переменных окружения при размещении
приложения.

Значения по умолчанию **не предусмотрены намеренно**. При отсутствии ключа
подписи либо при его длине менее 32 знаков приложение прекращает запуск
с сообщением, указывающим команду для задания значения. Значение по
умолчанию, пригодное для запуска, с высокой вероятностью осталось бы
неизменным при размещении приложения.

## Решение: журнал действий

Ведётся журнал действий, изменяющих состояние системы: входов в систему,
создания и изменения портфелей и позиций, загрузки данных из внешних
источников, управления учётными записями.

Назначение журнала в предметной области состоит не в контроле за
пользователями, а в **установлении причины изменения оценки риска**.
Изменение величины VaR по портфелю имеет одну из двух причин: изменение
рыночных условий либо изменение состава портфеля. Журнал позволяет
различить эти случаи.

Имя пользователя сохраняется в записи журнала, а не выбирается по ссылке
на учётную запись. Основание: журнал должен оставаться читаемым и после
того, как учётная запись помечена недействующей. По той же причине
учётные записи не удаляются, а переводятся в недействующие: удаление
нарушило бы связность журнала.

Запись входа в систему выполняется с явным указанием пользователя:
на момент проверки подлинности запрос ещё не содержит удостоверения,
и сведения о пользователе не могут быть получены из него. Первая
реализация этого не учитывала, и записи о входах содержали значение
«не определён».

## Решение: требования к паролю и противодействие подбору

Требования к паролю: не менее восьми знаков, наличие строчных и прописных
букв и цифр. Наличие особых знаков не требуется: это требование повышает
сложность запоминания, не повышая устойчивости к подбору соразмерно.

После пяти последовательных неудачных попыток вход блокируется на
пятнадцать минут. Сообщение об отказе не различает отсутствие учётной
записи и неверный пароль: различие позволило бы установить, какие имена
пользователей существуют в системе.

## Результаты апробации

Проверена матрица доступа по трём ролям. Знаком «+» обозначено выполнение
действия, знаком «−» — отказ с состоянием 403.

| Действие | Администратор | Аналитик | Наблюдатель |
| --- | :---: | :---: | :---: |
| Просмотр портфелей | + | + | + |
| Расчёт риска портфеля | + | + | + |
| Добавление позиции в собственный портфель | + | + | − |
| Добавление инструмента в справочник | + | − | − |
| Загрузка ключевой ставки | + | − | − |
| Просмотр журнала действий | + | − | − |
| Управление учётными записями | + | − | − |

Проверено правило принадлежности портфеля. Портфель создан пользователем
`analyst`; пользователь `analyst2`, обладающий той же ролью аналитика,
получил отказ с состоянием 403 при попытке удалить портфель и при попытке
добавить в него позицию. Владелец те же действия выполнил успешно.
Администратор удалил портфель, созданный другим пользователем, успешно.
Портфель, владелец которого не установлен, изменён пользователем
`analyst2` успешно.

Проверено требование подлинности: обращение к `/api/portfolios` без
маркера отклоняется с состоянием 401, с маркером — выполняется;
обращение к `/health` выполняется без маркера.

Записи журнала содержат имя пользователя, вид действия, вид и
идентификатор объекта, описание на русском языке, сетевой адрес и время.

## Последствия

Положительные:

- сведения о составе портфелей и величине принимаемого риска недоступны
  без проверки подлинности;
- разделение обязанностей между ведением справочника, аналитической
  работой и ознакомлением с результатами соответствует порядку работы
  подразделения управления риском;
- журнал действий позволяет установить причину изменения оценки риска;
- требование подлинности по умолчанию исключает оставление вновь
  добавленного метода без защиты.

Отрицательные и известные ограничения:

- выпущенный маркер невозможно отозвать до истечения срока действия;
  устранение потребовало бы ведения перечня отозванных маркеров либо
  перехода к паре «маркер доступа — маркер обновления» с коротким сроком
  действия первого;
- маркер хранится в локальном хранилище браузера и потому доступен
  сценариям, выполняющимся на странице; при размещении в сети общего
  пользования следует перейти к хранению в защищённом куки-файле
  с признаками `HttpOnly` и `SameSite`;
- обмен с программным интерфейсом в среде разработки выполняется по
  незащищённому протоколу; при размещении требуется TLS, без которого
  маркер может быть перехвачен;
- изменение роли существующего пользователя через интерфейс не
  предусмотрено: учётная запись создаётся с одной ролью;
- журнал действий не содержит прежних и новых значений изменённых
  реквизитов: фиксируется факт изменения, но не его содержание.
