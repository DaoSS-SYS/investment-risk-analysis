## Общая картина

Система состоит из пяти проектов. Главное, что нужно понимать — **направление
зависимостей**: стрелка означает «знает о существовании».

```
WebApi ──> Application ──> Domain
   │            │
   │            └────────> RiskEngine        (математика, ни от чего не зависит)
   │
   └──────> Infrastructure ──> Domain, Application
```

Зачем так. Проект `RiskEngine` — это математические модели: VaR, волатильность,
коэффициенты. Он не знает ни про базу данных, ни про HTTP, ни даже про сущности
предметной области. Принимает массивы чисел, возвращает числа. Благодаря этому:

- его можно проверить тестами, не поднимая ни базу, ни веб-сервер;
- в тексте работы он описывается как самостоятельный компонент — «расчётное
  ядро системы»;
- если завтра заменить PostgreSQL на что угодно, математика не изменится
  ни на строчку.

Это решение записано в [ADR-0002](adr/0002-sloistaya-arhitektura.md).

**Что такое ADR.** Architecture Decision Record — запись об архитектурном
решении в формате «контекст → решение → последствия». Лежат в `docs/adr/`.
Методичка кафедры прямо рекомендует этот метод. Практическая польза: к декабрю
у тебя будет готовый материал для параграфов 2.1 и 2.3, написанный по ходу
дела, а не восстановленный задним числом.

## Этап 1. Каркас решения и модель данных

**Коммит:** `Этап 1: каркас решения, модель данных, первая миграция`

### Что сделано

Создано решение из пяти проектов, описаны семь сущностей предметной области,
сгенерирована и применена первая миграция базы данных, поднят программный
интерфейс со Swagger и проверкой работоспособности.

### Где что лежит

| Файл | Что делает |
| --- | --- |
| `backend/RiskAnalysis.sln` | Файл решения, связывает пять проектов |
| `backend/global.json` | Фиксирует версию .NET SDK, чтобы сборка была воспроизводимой |
| `Domain/Entities/*.cs` | Семь классов сущностей — из них порождается схема БД |
| `Domain/Enums/DomainEnums.cs` | Перечисления: тип бумаги, вид расчёта, статус |
| `Infrastructure/Persistence/RiskAnalysisDbContext.cs` | Контекст базы данных |
| `Infrastructure/Persistence/Configurations/*.cs` | Настройка каждой таблицы: типы, индексы, связи |
| `Infrastructure/Persistence/Migrations/` | Сгенерированные миграции |
| `Infrastructure/DependencyInjection.cs` | Регистрация всех сервисов в контейнере |
| `WebApi/Program.cs` | Точка входа: что подключено и в каком порядке |
| `WebApi/Controllers/SystemController.cs` | Служебный метод `/api/system/info` |

### Как это работает

**Code First.** Схема базы данных не пишется руками на SQL. Пишутся классы:

```csharp
public class Quote
{
    public long Id { get; set; }
    public int InstrumentId { get; set; }
    public DateOnly TradeDate { get; set; }
    public decimal Close { get; set; }
    // ...
}
```

Дальше команда `dotnet ef migrations add ИмяМиграции` сравнивает классы с
предыдущим состоянием и генерирует код изменения схемы. Команда
`dotnet ef database update` применяет его к базе.

Почему не наоборот (Database First): схема меняется многократно — подсистемы
аутентификации, бэктестинга, стресс-тестирования добавляются поэтапно. История
миграций лежит в репозитории и датирована, а развёртывание на чужой машине
делается одной командой.

**Конфигурация вынесена из контекста.** Вместо того чтобы настраивать все
таблицы в одном методе `OnModelCreating`, на каждую сущность заведён отдельный
класс:

```csharp
public class QuoteConfiguration : IEntityTypeConfiguration<Quote>
{
    public void Configure(EntityTypeBuilder<Quote> builder)
    {
        builder.Property(x => x.Close).HasPrecision(18, 6).IsRequired();
        builder.HasIndex(x => new { x.InstrumentId, x.TradeDate }).IsUnique();
    }
}
```

а контекст подхватывает их автоматически:

```csharp
modelBuilder.ApplyConfigurationsFromAssembly(typeof(RiskAnalysisDbContext).Assembly);
```

**Именование snake_case.** Пакет `EFCore.NamingConventions` превращает
`TradeDate` в `trade_date`, `ImportLog` в `import_logs`. Это соглашение
PostgreSQL: без него пришлось бы писать `SELECT "TradeDate"` в кавычках.

**Фабрика контекста для миграций.** Файл `RiskAnalysisDbContextFactory.cs`
нужен, чтобы `dotnet ef` мог создать контекст, не запуская веб-приложение и не
требуя строки подключения из конфигурации. Строку берёт из переменной окружения
`RISKANALYSIS_CONNECTION`, при её отсутствии подставляет значение по умолчанию —
для генерации кода миграции подключение к базе не требуется вовсе.

### Схема данных

Семь таблиц:

| Таблица | Назначение | Ключевая особенность |
| --- | --- | --- |
| `instruments` | Справочник бумаг | Уникальность по паре тикер + режим торгов |
| `quotes` | Дневные свечи | **Уникальный индекс `(instrument_id, trade_date)`** |
| `macro_indicators` | Ключевая ставка ЦБ, курсы | Безрисковая ставка для Шарпа и CAPM |
| `portfolios` | Портфели | Ссылка на бенчмарк (IMOEX) |
| `positions` | Позиции портфеля | Допускает несколько лотов одной бумаги |
| `risk_calculations` | Журнал расчётов | Параметры и результат в `jsonb`, `duration_ms` |
| `import_logs` | Журнал загрузок | Диагностика отказов источника |

Два решения, которые нужно уметь объяснить.

**Почему `jsonb`, а не отдельная таблица под каждый метод.** У параметрического
VaR параметры — уровень доверия, горизонт, глубина выборки. У Монте-Карло
добавляются число сценариев и зерно генератора. У бэктеста — период проверки и
проверяемый метод. Отдельная таблица на каждый метод означала бы семь с лишним
таблиц с пересекающимися полями и новую миграцию на каждую добавленную модель.
В `jsonb` структура задаётся типами C# и проверяется при десериализации.
Подробно — [ADR-0005](adr/0005-hranenie-parametrov-raschetov.md).

**Зачем `duration_ms` в журнале расчётов.** Параграф 3.3 требует оценки
производительности системы. Поле заведено сразу, чтобы к декабрю в базе уже
накопились реальные замеры, а не пришлось их специально собирать.

### Обвязка в `Program.cs`

Порядок в файле — это порядок конвейера обработки запроса:

```
Serilog          → журналирование в консоль и файл
AddInfrastructure→ база данных и внешние источники
AddControllers   → контроллеры; перечисления сериализуются строками
AddSwaggerGen    → документация интерфейса из XML-комментариев
AddHealthChecks  → проверка доступности базы: /health
AddCors          → разрешение запросов с клиентского приложения
```

Перечисления передаются строками (`"Share"`, а не `1`) — ответы интерфейса
становятся самодокументируемыми, и клиенту на React не нужно знать числовые коды.

### Что спросят на защите

**«Почему пять проектов, а не один?»** Расчётное ядро изолировано от базы и
сети, поэтому математические модели проверяются модульными тестами без
развёрнутой СУБД, а в работе описываются как самостоятельный компонент.

**«Почему Code First?»** Схема менялась многократно по ходу разработки.
История изменений датирована и лежит в репозитории, развёртывание на чужой
машине — одна команда.

**«Зачем уникальный индекс на котировках?»** Он делает загрузку данных
идемпотентной: повторный запуск за тот же период физически не может создать
дубликат. Подробнее — этап 2.

## Этап 2. Загрузка котировок из MOEX ISS

**Коммит:** `Этап 2: загрузка котировок из MOEX ISS`

### Что сделано

Клиент информационно-статистического сервера Московской Биржи, подсистема
идемпотентной загрузки с журналированием, методы интерфейса для справочника и
котировок. Загружено 15 081 котировка по шести инструментам за десять лет.

### Где что лежит

| Файл | Что делает |
| --- | --- |
| `Application/Abstractions/IMarketDataClient.cs` | Интерфейс источника рыночных данных |
| `Application/Abstractions/IQuoteImportService.cs` | Интерфейс подсистемы загрузки |
| `Application/Models/MarketQuote.cs` | Котировка от источника до сохранения |
| `Application/Models/SecurityInfo.cs` | Бумага из справочника биржи |
| `Application/Models/ImportResult.cs` | Итог сеанса загрузки |
| `Infrastructure/ExternalData/Moex/MoexIssClient.cs` | Реализация клиента MOEX |
| `Infrastructure/ExternalData/Moex/MoexIssOptions.cs` | Настройки: адрес, таймаут, повторы |
| `Infrastructure/Services/QuoteImportService.cs` | Загрузка, сверка, журналирование |
| `WebApi/Controllers/InstrumentsController.cs` | Справочник, поиск, импорт, котировки |
| `WebApi/Controllers/ImportController.cs` | Массовая загрузка и журнал |

### Почему интерфейс, а реализация отдельно

`IMarketDataClient` лежит в `Application`, `MoexIssClient` — в
`Infrastructure`. Слой приложения знает, что источник данных существует и что у
него можно запросить историю, но не знает, что это именно Московская Биржа.
Добавить второй источник — значит написать ещё одну реализацию интерфейса,
не трогая ничего остального.

### Три вещи в клиенте MOEX, которые нужно понимать

**1. Разбор по именам столбцов, а не по позициям.**

Сервер отдаёт данные таблицей: отдельно массив имён столбцов, отдельно массив
строк.

```json
{
  "history": {
    "columns": ["BOARDID", "TRADEDATE", "OPEN", "CLOSE", "VOLUME", ...],
    "data": [["TQBR", "2026-09-01", 276.03, 272.21, 26826095, ...]]
  }
}
```

Соблазнительно читать `row[3]` для цены закрытия. Так делать нельзя: у рынка
акций 24 столбца в одном порядке, у рынка индексов 20 столбцов в другом.
Привязка к позициям сломалась бы на первом же индексе.

Поэтому строится словарь «имя столбца → его номер»:

```csharp
private static Dictionary<string, int> BuildColumnIndex(JsonElement columns)
```

и дальше значения читаются по имени: `ReadDecimal(row, columns, "CLOSE")`.

**2. Постраничная выдача.**

Биржа отдаёт максимум 100 записей за запрос. Сколько всего записей и какой
размер страницы — сообщается в служебном блоке `history.cursor`:

```json
"history.cursor": { "columns": ["INDEX","TOTAL","PAGESIZE"], "data": [[0, 2514, 100]] }
```

Клиент крутит цикл, увеличивая параметр `start`, пока не выберет всё. Десять лет
по одной бумаге — примерно 25 запросов. Между запросами пауза 100 мс, чтобы не
создавать нагрузку на публичный сервис.

**3. Повторные попытки.**

Метод `GetJsonAsync` повторяет запрос при кодах 5xx, коде 429 (слишком много
запросов), ошибках передачи и превышении времени ожидания. Задержка растёт с
номером попытки. Ошибки, которые повторять бессмысленно — например, 404 —
выбрасываются сразу.

Это материал для раздела о надёжности системы: внешний источник может быть
недоступен, и система должна вести себя предсказуемо.

### Идемпотентность загрузки

**Задача.** Загрузка одного и того же периода выполняется многократно: по
расписанию, вручную, при довыгрузке. Кроме того, биржа пересматривает итоги
торгов последних дней. Повторный запуск не должен ни плодить дубликаты, ни
терять уточнённые значения.

**Решение на двух уровнях.**

Первый — база данных:

```csharp
builder.HasIndex(x => new { x.InstrumentId, x.TradeDate }).IsUnique();
```

Дубликат физически невозможен, даже если два процесса запустят загрузку
одновременно.

Второй — приложение. В `QuoteImportService` существующие котировки за период
выбираются **одним запросом** в словарь по дате:

```csharp
var existing = await _db.Quotes
    .Where(q => q.InstrumentId == instrument.Id
                && q.TradeDate >= from && q.TradeDate <= to)
    .ToDictionaryAsync(q => q.TradeDate, cancellationToken);
```

Дальше по каждой полученной записи:

- даты нет в словаре → добавляем;
- дата есть, значения совпадают → пропускаем;
- дата есть, значения отличаются → обновляем.

Почему словарём, а не запросом по каждой записи: 2514 обращений к базе вместо
одного — это разница между пятью секундами и несколькими минутами.

**Проверено.** Повторная загрузка тех же десяти лет по SBER:
получено 2514, добавлено 0, обновлено 0.

### Журнал загрузок

Каждый сеанс пишется в `import_logs`: источник, инструмент, период, сколько
получено, добавлено и обновлено, статус, длительность. Отказы записываются
тоже — в блоке `catch` контекст изменений очищается и сохраняется только запись
журнала, чтобы неудачная попытка не осталась незафиксированной.

### Автономность

Все котировки лежат в базе, и расчёты выполняются **только** по сохранённым
данным. К бирже система обращается исключительно на этапе загрузки. Это
принципиально: на защите может не быть интернета, а MOEX может ответить
ошибкой. Система должна работать полностью автономно.

### Что спросят на защите

**«Почему данные хранятся у вас, а не запрашиваются при расчёте?»**
Автономность работы и воспроизводимость результатов: расчёт, выполненный
сегодня и через месяц на тех же параметрах, даст тот же результат.

**«Что будет, если биржа недоступна?»** Клиент выполнит три попытки с
нарастающей задержкой, после чего сеанс будет зафиксирован в журнале со
статусом отказа. Расчётная часть продолжит работать на ранее загруженных данных.

**«Почему вы читаете JSON по именам столбцов?»** Состав и порядок столбцов
различаются по рынкам биржи; привязка к позициям неработоспособна.

## Этап 2.5. Предобработка данных

**Коммит:** `Этап 2.5: предобработка данных — корпоративные действия`

Этот этап не планировался. Он появился после того, как загруженные данные были
проверены на аномалии.

### Проблема

Биржа публикует котировки в том виде, в каком шли торги, без корректировки на
корпоративные действия. Запрос к загруженной истории на однодневные изменения
цены больше 30 процентов дал:

| Тикер | Дата | Было | Стало | Изменение |
| --- | --- | --- | --- | --- |
| **GMKN** | 08.04.2024 | 15 054 | 152,96 | **−98,98 %** |
| SBER | 24.02.2022 | 208,53 | 132,18 | −36,61 % |
| ROSN | 24.02.2022 | 431,30 | 274,70 | −36,31 % |
| IMOEX | 24.02.2022 | 3 084,74 | 2 058,12 | −33,28 % |
| GAZP | 30.06.2022 | 297,65 | 207,00 | −30,46 % |

Первая строка — **дробление акций Норникеля 1 к 100**. Цена упала в сто раз,
стоимость позиции инвестора не изменилась ни на копейку. Логарифмическая
доходность этого дня равна −4,5892.

Остальные строки — **настоящие рыночные события**: 24 февраля 2022 года и отказ
Газпрома от дивидендов.

### Почему это критично

Измерено на 2514 дневных доходностях GMKN:

| Показатель | Без корректировки | С корректировкой |
| --- | --- | --- |
| Волатильность (годовая) | **148,73 %** | **31,07 %** |
| Коэффициент эксцесса | 2290,0 | 7,4 |
| Минимальная дневная доходность | −4,5892 | −0,1574 |

Волатильность завышается **в 4,79 раза**. От неё зависят параметрический VaR,
Монте-Карло, ковариационная матрица портфеля и все коэффициенты эффективности —
то есть вообще вся расчётная часть.

Хуже всего то, что **ошибка не вызывает отказа**. Расчёт отработает успешно и
вернёт правдоподобные по форме числа. Обнаружить это можно только проверкой
данных.

### Решение, которое было бы неправильным

Отбросить все значения за порогом как выбросы.

Тот же порог отбирает 24 февраля 2022 года. А это ровно те наблюдения, ради
которых берутся десять лет истории: «тяжёлые хвосты» распределения, которые
обосновывают переход от параметрического VaR к историческому, и готовые
исторические сценарии стресс-тестирования.

**Задача не в том, чтобы убрать выбросы, а в том, чтобы отличить техническую
аномалию от рыночного события.**

### Алгоритм

Файл `Infrastructure/Services/CorporateActionService.cs`.

Шаг 1. Для каждой пары соседних котировок считается логарифмическая доходность.
Если её модуль не превышает порога 0,40 — идём дальше.

```csharp
private const double AnomalyThreshold = 0.40;
```

Порог 0,40 — это примерно −33 % или +49 % за день.

Шаг 2. Направление изменения определяет вид действия: падение цены —
кандидат на дробление, рост — на консолидацию.

Шаг 3. Наблюдаемое отношение цен сравнивается с коэффициентами, применяемыми
на практике:

```csharp
private static readonly decimal[] KnownRatios =
    [2m, 3m, 4m, 5m, 6m, 8m, 10m, 20m, 50m, 100m, 1000m];
```

Шаг 4. Если отношение совпало с одним из коэффициентов с отклонением не более
5 процентов — это корпоративное действие. Допуск нужен потому, что в день
дробления цена меняется ещё и от торгов: у Норникеля наблюдаемое отношение
вышло 98,42 при коэффициенте 100, то есть отклонение 1,58 процента.

Шаг 5. Не совпало — рыночное событие, корректировка не применяется.

**Результат работы алгоритма на реальных данных:**

```
GMKN   2024-04-08  15054.00 ->  152.96  ln(r)=-4.5892  [Split]
IMOEX  2022-02-24   3084.74 -> 2058.12  ln(r)=-0.4047  [MarketEvent]
ROSN   2022-02-24    431.30 ->  274.70  ln(r)=-0.4511  [MarketEvent]
SBER   2022-02-24    208.53 ->  132.18  ln(r)=-0.4559  [MarketEvent]
```

Для SBER отношение 208,53 / 132,18 = 1,5776 — ближайший коэффициент 2,
отклонение 21 процент, значительно больше допуска. Поэтому рыночное событие.

### Как применяется корректировка

Исходные котировки **не изменяются никогда**. Корректировка применяется при
построении ценового ряда — файл `Infrastructure/Services/PriceSeriesService.cs`.

Правило: все котировки **до** даты корпоративного действия умножаются на
корректирующий множитель. Для дробления 1 к 100 множитель равен 0,01.

Ряд обходится от последней даты к первой с накоплением произведения:

```csharp
for (var i = quotes.Count - 1; i >= 0; i--)
{
    var (date, close) = quotes[i];

    while (adjustmentIndex < adjustments.Count &&
           adjustments[adjustmentIndex].Date > date)
    {
        cumulativeFactor *= adjustments[adjustmentIndex].Factor;
        adjustmentIndex++;
    }

    points[i] = new PricePoint(date, close, close * cumulativeFactor);
}
```

Обход в обратную сторону нужен, чтобы при нескольких дроблениях к ранним
котировкам автоматически применялось произведение всех последующих множителей.
Сложность линейная по длине ряда.

**Проверка на GMKN:**

```
дата          close(биржа)   adjustedClose   ln(r) исх.   ln(r) скорр.
2024-04-01        15054.00        150.5400      -0.0037        -0.0037
2024-04-08          152.96        152.9600      -4.5892        +0.0159   <- дробление
2024-04-09          164.00        164.0000      +0.0697        +0.0697
```

Доходность дня дробления превратилась из −4,5892 в +0,0159. Это реальное
движение цены за период приостановки торгов (со 2 по 5 апреля торги не велись).

### Единственная точка доступа к ценам

Интерфейс `IPriceSeriesProvider` — **единственный** способ, которым расчётная
часть получает цены. Напрямую к таблице `quotes` расчёты не обращаются. Это
гарантирует, что нескорректированные данные в модель не попадут физически.

У него два метода:

- `GetSeriesAsync` — ряд одного инструмента;
- `GetAlignedSeriesAsync` — ряды нескольких инструментов, приведённые к общему
  торговому календарю.

Второй понадобится на этапе расчёта ковариационной матрицы портфеля. Если у
одной бумаги торги приостанавливались, а у другой нет, то без выравнивания
календарей доходности разных торговых дней окажутся сопоставлены друг с другом,
и корреляции будут посчитаны неверно. Метод берёт пересечение дат по всем
инструментам.

### Хранение и ручное переопределение

Все найденные аномалии пишутся в таблицу `corporate_actions`, включая
признанные рыночными событиями. Это документирует, что каждое наблюдение было
проверено, а не пропущено.

Поля:

- `action_type` — Split, ReverseSplit или MarketEvent;
- `ratio` — коэффициент (100 для дробления Норникеля);
- `adjustment_factor` — множитель для более ранних котировок (0,01);
- `observed_ratio`, `observed_log_return` — исходное наблюдение, на основании
  которого принято решение;
- `source` — Automatic или Manual;
- `is_confirmed` — подтверждено ли пользователем;
- `is_applied` — применять ли корректировку;
- `comment` — текстовое обоснование, формируется алгоритмом.

Автоматическая классификация ставит `is_confirmed = false`, но
`is_applied = true` для корпоративных действий: иначе расчёты по умолчанию шли
бы на заведомо испорченных данных. Пользователь может изменить классификацию
методом `PUT /api/corporate-actions/{id}` — запись помечается как внесённая
вручную и при повторных запусках выявления не перезаписывается.

### Известное ограничение: дивидендные разрывы

В день закрытия реестра цена падает примерно на величину дивиденда. Для
российского рынка это единицы процентов — порог 0,40 такое не ловит.

Это **сознательно оставлено** и зафиксировано как ограничение в
[ADR-0007](adr/0007-korporativnye-dejstviya.md). Честно названное ограничение
на защите вопросов не вызывает, а необнаруженная ошибка — вызывает.

### Что спросят на защите

**«Почему вы не удалили выбросы?»** Потому что среди них есть настоящие
рыночные шоки, которые составляют предмет исследования. Задача — отличить
техническую аномалию от рыночного события, а не убрать все крайние значения.

**«Как вы отличаете дробление от падения рынка?»** По совпадению отношения цен
с коэффициентом дробления в пределах допуска 5 процентов. У Норникеля
отношение 98,42 при коэффициенте 100 — совпало. У Сбербанка 1,5776 против
ближайшего коэффициента 2 — отклонение 21 процент, не совпало.

**«Вы меняете исходные данные?»** Нет. Котировки хранятся в том виде, в каком
их опубликовала биржа. Корректировка применяется при построении ряда для
расчёта и полностью обратима.

**«Насколько это вообще важно?»** Без корректировки годовая волатильность GMKN
оценивается в 148,73 процента вместо 31,07 — завышение в 4,79 раза. При этом
расчёт не выдаёт ошибки, результат выглядит правдоподобно.
