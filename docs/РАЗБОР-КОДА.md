## Общая картина

Система состоит из пяти проектов. Главное, что нужно понимать — **направление
зависимостей**: стрелка означает «знает о существовании».

```
WebApi ──> Application ──> Domain
   │            │
   │            └────────> RiskEngine        (математика, ни от чего не зависит)
   │
   └──────> Infrastructure ──> Domain, Application
```

Зачем так. Проект `RiskEngine` — это математические модели: VaR, волатильность,
коэффициенты. Он не знает ни про базу данных, ни про HTTP, ни даже про сущности
предметной области. Принимает массивы чисел, возвращает числа. Благодаря этому:

- его можно проверить тестами, не поднимая ни базу, ни веб-сервер;
- в тексте работы он описывается как самостоятельный компонент — «расчётное
  ядро системы»;
- если завтра заменить PostgreSQL на что угодно, математика не изменится
  ни на строчку.

Это решение записано в [ADR-0002](adr/0002-sloistaya-arhitektura.md).

**Что такое ADR.** Architecture Decision Record — запись об архитектурном
решении в формате «контекст → решение → последствия». Лежат в `docs/adr/`.
Методичка кафедры прямо рекомендует этот метод. Практическая польза: к декабрю
у тебя будет готовый материал для параграфов 2.1 и 2.3, написанный по ходу
дела, а не восстановленный задним числом.

## Этап 1. Каркас решения и модель данных

**Коммит:** `Этап 1: каркас решения, модель данных, первая миграция`

### Что сделано

Создано решение из пяти проектов, описаны семь сущностей предметной области,
сгенерирована и применена первая миграция базы данных, поднят программный
интерфейс со Swagger и проверкой работоспособности.

### Где что лежит

| Файл | Что делает |
| --- | --- |
| `backend/RiskAnalysis.sln` | Файл решения, связывает пять проектов |
| `backend/global.json` | Фиксирует версию .NET SDK, чтобы сборка была воспроизводимой |
| `Domain/Entities/*.cs` | Семь классов сущностей — из них порождается схема БД |
| `Domain/Enums/DomainEnums.cs` | Перечисления: тип бумаги, вид расчёта, статус |
| `Infrastructure/Persistence/RiskAnalysisDbContext.cs` | Контекст базы данных |
| `Infrastructure/Persistence/Configurations/*.cs` | Настройка каждой таблицы: типы, индексы, связи |
| `Infrastructure/Persistence/Migrations/` | Сгенерированные миграции |
| `Infrastructure/DependencyInjection.cs` | Регистрация всех сервисов в контейнере |
| `WebApi/Program.cs` | Точка входа: что подключено и в каком порядке |
| `WebApi/Controllers/SystemController.cs` | Служебный метод `/api/system/info` |

### Как это работает

**Code First.** Схема базы данных не пишется руками на SQL. Пишутся классы:

```csharp
public class Quote
{
    public long Id { get; set; }
    public int InstrumentId { get; set; }
    public DateOnly TradeDate { get; set; }
    public decimal Close { get; set; }
    // ...
}
```

Дальше команда `dotnet ef migrations add ИмяМиграции` сравнивает классы с
предыдущим состоянием и генерирует код изменения схемы. Команда
`dotnet ef database update` применяет его к базе.

Почему не наоборот (Database First): схема меняется многократно — подсистемы
аутентификации, бэктестинга, стресс-тестирования добавляются поэтапно. История
миграций лежит в репозитории и датирована, а развёртывание на чужой машине
делается одной командой.

**Конфигурация вынесена из контекста.** Вместо того чтобы настраивать все
таблицы в одном методе `OnModelCreating`, на каждую сущность заведён отдельный
класс:

```csharp
public class QuoteConfiguration : IEntityTypeConfiguration<Quote>
{
    public void Configure(EntityTypeBuilder<Quote> builder)
    {
        builder.Property(x => x.Close).HasPrecision(18, 6).IsRequired();
        builder.HasIndex(x => new { x.InstrumentId, x.TradeDate }).IsUnique();
    }
}
```

а контекст подхватывает их автоматически:

```csharp
modelBuilder.ApplyConfigurationsFromAssembly(typeof(RiskAnalysisDbContext).Assembly);
```

**Именование snake_case.** Пакет `EFCore.NamingConventions` превращает
`TradeDate` в `trade_date`, `ImportLog` в `import_logs`. Это соглашение
PostgreSQL: без него пришлось бы писать `SELECT "TradeDate"` в кавычках.

**Фабрика контекста для миграций.** Файл `RiskAnalysisDbContextFactory.cs`
нужен, чтобы `dotnet ef` мог создать контекст, не запуская веб-приложение и не
требуя строки подключения из конфигурации. Строку берёт из переменной окружения
`RISKANALYSIS_CONNECTION`, при её отсутствии подставляет значение по умолчанию —
для генерации кода миграции подключение к базе не требуется вовсе.

### Схема данных

Семь таблиц:

| Таблица | Назначение | Ключевая особенность |
| --- | --- | --- |
| `instruments` | Справочник бумаг | Уникальность по паре тикер + режим торгов |
| `quotes` | Дневные свечи | **Уникальный индекс `(instrument_id, trade_date)`** |
| `macro_indicators` | Ключевая ставка ЦБ, курсы | Безрисковая ставка для Шарпа и CAPM |
| `portfolios` | Портфели | Ссылка на бенчмарк (IMOEX) |
| `positions` | Позиции портфеля | Допускает несколько лотов одной бумаги |
| `risk_calculations` | Журнал расчётов | Параметры и результат в `jsonb`, `duration_ms` |
| `import_logs` | Журнал загрузок | Диагностика отказов источника |

Два решения, которые нужно уметь объяснить.

**Почему `jsonb`, а не отдельная таблица под каждый метод.** У параметрического
VaR параметры — уровень доверия, горизонт, глубина выборки. У Монте-Карло
добавляются число сценариев и зерно генератора. У бэктеста — период проверки и
проверяемый метод. Отдельная таблица на каждый метод означала бы семь с лишним
таблиц с пересекающимися полями и новую миграцию на каждую добавленную модель.
В `jsonb` структура задаётся типами C# и проверяется при десериализации.
Подробно — [ADR-0005](adr/0005-hranenie-parametrov-raschetov.md).

**Зачем `duration_ms` в журнале расчётов.** Параграф 3.3 требует оценки
производительности системы. Поле заведено сразу, чтобы к декабрю в базе уже
накопились реальные замеры, а не пришлось их специально собирать.

### Обвязка в `Program.cs`

Порядок в файле — это порядок конвейера обработки запроса:

```
Serilog          → журналирование в консоль и файл
AddInfrastructure→ база данных и внешние источники
AddControllers   → контроллеры; перечисления сериализуются строками
AddSwaggerGen    → документация интерфейса из XML-комментариев
AddHealthChecks  → проверка доступности базы: /health
AddCors          → разрешение запросов с клиентского приложения
```

Перечисления передаются строками (`"Share"`, а не `1`) — ответы интерфейса
становятся самодокументируемыми, и клиенту на React не нужно знать числовые коды.

### Что спросят на защите

**«Почему пять проектов, а не один?»** Расчётное ядро изолировано от базы и
сети, поэтому математические модели проверяются модульными тестами без
развёрнутой СУБД, а в работе описываются как самостоятельный компонент.

**«Почему Code First?»** Схема менялась многократно по ходу разработки.
История изменений датирована и лежит в репозитории, развёртывание на чужой
машине — одна команда.

**«Зачем уникальный индекс на котировках?»** Он делает загрузку данных
идемпотентной: повторный запуск за тот же период физически не может создать
дубликат. Подробнее — этап 2.

## Этап 2. Загрузка котировок из MOEX ISS

**Коммит:** `Этап 2: загрузка котировок из MOEX ISS`

### Что сделано

Клиент информационно-статистического сервера Московской Биржи, подсистема
идемпотентной загрузки с журналированием, методы интерфейса для справочника и
котировок. Загружено 15 081 котировка по шести инструментам за десять лет.

### Где что лежит

| Файл | Что делает |
| --- | --- |
| `Application/Abstractions/IMarketDataClient.cs` | Интерфейс источника рыночных данных |
| `Application/Abstractions/IQuoteImportService.cs` | Интерфейс подсистемы загрузки |
| `Application/Models/MarketQuote.cs` | Котировка от источника до сохранения |
| `Application/Models/SecurityInfo.cs` | Бумага из справочника биржи |
| `Application/Models/ImportResult.cs` | Итог сеанса загрузки |
| `Infrastructure/ExternalData/Moex/MoexIssClient.cs` | Реализация клиента MOEX |
| `Infrastructure/ExternalData/Moex/MoexIssOptions.cs` | Настройки: адрес, таймаут, повторы |
| `Infrastructure/Services/QuoteImportService.cs` | Загрузка, сверка, журналирование |
| `WebApi/Controllers/InstrumentsController.cs` | Справочник, поиск, импорт, котировки |
| `WebApi/Controllers/ImportController.cs` | Массовая загрузка и журнал |

### Почему интерфейс, а реализация отдельно

`IMarketDataClient` лежит в `Application`, `MoexIssClient` — в
`Infrastructure`. Слой приложения знает, что источник данных существует и что у
него можно запросить историю, но не знает, что это именно Московская Биржа.
Добавить второй источник — значит написать ещё одну реализацию интерфейса,
не трогая ничего остального.

### Три вещи в клиенте MOEX, которые нужно понимать

**1. Разбор по именам столбцов, а не по позициям.**

Сервер отдаёт данные таблицей: отдельно массив имён столбцов, отдельно массив
строк.

```json
{
  "history": {
    "columns": ["BOARDID", "TRADEDATE", "OPEN", "CLOSE", "VOLUME", ...],
    "data": [["TQBR", "2026-09-01", 276.03, 272.21, 26826095, ...]]
  }
}
```

Соблазнительно читать `row[3]` для цены закрытия. Так делать нельзя: у рынка
акций 24 столбца в одном порядке, у рынка индексов 20 столбцов в другом.
Привязка к позициям сломалась бы на первом же индексе.

Поэтому строится словарь «имя столбца → его номер»:

```csharp
private static Dictionary<string, int> BuildColumnIndex(JsonElement columns)
```

и дальше значения читаются по имени: `ReadDecimal(row, columns, "CLOSE")`.

**2. Постраничная выдача.**

Биржа отдаёт максимум 100 записей за запрос. Сколько всего записей и какой
размер страницы — сообщается в служебном блоке `history.cursor`:

```json
"history.cursor": { "columns": ["INDEX","TOTAL","PAGESIZE"], "data": [[0, 2514, 100]] }
```

Клиент крутит цикл, увеличивая параметр `start`, пока не выберет всё. Десять лет
по одной бумаге — примерно 25 запросов. Между запросами пауза 100 мс, чтобы не
создавать нагрузку на публичный сервис.

**3. Повторные попытки.**

Метод `GetJsonAsync` повторяет запрос при кодах 5xx, коде 429 (слишком много
запросов), ошибках передачи и превышении времени ожидания. Задержка растёт с
номером попытки. Ошибки, которые повторять бессмысленно — например, 404 —
выбрасываются сразу.

Это материал для раздела о надёжности системы: внешний источник может быть
недоступен, и система должна вести себя предсказуемо.

### Идемпотентность загрузки

**Задача.** Загрузка одного и того же периода выполняется многократно: по
расписанию, вручную, при довыгрузке. Кроме того, биржа пересматривает итоги
торгов последних дней. Повторный запуск не должен ни плодить дубликаты, ни
терять уточнённые значения.

**Решение на двух уровнях.**

Первый — база данных:

```csharp
builder.HasIndex(x => new { x.InstrumentId, x.TradeDate }).IsUnique();
```

Дубликат физически невозможен, даже если два процесса запустят загрузку
одновременно.

Второй — приложение. В `QuoteImportService` существующие котировки за период
выбираются **одним запросом** в словарь по дате:

```csharp
var existing = await _db.Quotes
    .Where(q => q.InstrumentId == instrument.Id
                && q.TradeDate >= from && q.TradeDate <= to)
    .ToDictionaryAsync(q => q.TradeDate, cancellationToken);
```

Дальше по каждой полученной записи:

- даты нет в словаре → добавляем;
- дата есть, значения совпадают → пропускаем;
- дата есть, значения отличаются → обновляем.

Почему словарём, а не запросом по каждой записи: 2514 обращений к базе вместо
одного — это разница между пятью секундами и несколькими минутами.

**Проверено.** Повторная загрузка тех же десяти лет по SBER:
получено 2514, добавлено 0, обновлено 0.

### Журнал загрузок

Каждый сеанс пишется в `import_logs`: источник, инструмент, период, сколько
получено, добавлено и обновлено, статус, длительность. Отказы записываются
тоже — в блоке `catch` контекст изменений очищается и сохраняется только запись
журнала, чтобы неудачная попытка не осталась незафиксированной.

### Автономность

Все котировки лежат в базе, и расчёты выполняются **только** по сохранённым
данным. К бирже система обращается исключительно на этапе загрузки. Это
принципиально: на защите может не быть интернета, а MOEX может ответить
ошибкой. Система должна работать полностью автономно.

### Что спросят на защите

**«Почему данные хранятся у вас, а не запрашиваются при расчёте?»**
Автономность работы и воспроизводимость результатов: расчёт, выполненный
сегодня и через месяц на тех же параметрах, даст тот же результат.

**«Что будет, если биржа недоступна?»** Клиент выполнит три попытки с
нарастающей задержкой, после чего сеанс будет зафиксирован в журнале со
статусом отказа. Расчётная часть продолжит работать на ранее загруженных данных.

**«Почему вы читаете JSON по именам столбцов?»** Состав и порядок столбцов
различаются по рынкам биржи; привязка к позициям неработоспособна.

## Этап 2.5. Предобработка данных

**Коммит:** `Этап 2.5: предобработка данных — корпоративные действия`

Этот этап не планировался. Он появился после того, как загруженные данные были
проверены на аномалии.

### Проблема

Биржа публикует котировки в том виде, в каком шли торги, без корректировки на
корпоративные действия. Запрос к загруженной истории на однодневные изменения
цены больше 30 процентов дал:

| Тикер | Дата | Было | Стало | Изменение |
| --- | --- | --- | --- | --- |
| **GMKN** | 08.04.2024 | 15 054 | 152,96 | **−98,98 %** |
| SBER | 24.02.2022 | 208,53 | 132,18 | −36,61 % |
| ROSN | 24.02.2022 | 431,30 | 274,70 | −36,31 % |
| IMOEX | 24.02.2022 | 3 084,74 | 2 058,12 | −33,28 % |
| GAZP | 30.06.2022 | 297,65 | 207,00 | −30,46 % |

Первая строка — **дробление акций Норникеля 1 к 100**. Цена упала в сто раз,
стоимость позиции инвестора не изменилась ни на копейку. Логарифмическая
доходность этого дня равна −4,5892.

Остальные строки — **настоящие рыночные события**: 24 февраля 2022 года и отказ
Газпрома от дивидендов.

### Почему это критично

Измерено на 2514 дневных доходностях GMKN:

| Показатель | Без корректировки | С корректировкой |
| --- | --- | --- |
| Волатильность (годовая) | **148,73 %** | **31,07 %** |
| Коэффициент эксцесса | 2290,0 | 7,4 |
| Минимальная дневная доходность | −4,5892 | −0,1574 |

Волатильность завышается **в 4,79 раза**. От неё зависят параметрический VaR,
Монте-Карло, ковариационная матрица портфеля и все коэффициенты эффективности —
то есть вообще вся расчётная часть.

Хуже всего то, что **ошибка не вызывает отказа**. Расчёт отработает успешно и
вернёт правдоподобные по форме числа. Обнаружить это можно только проверкой
данных.

### Решение, которое было бы неправильным

Отбросить все значения за порогом как выбросы.

Тот же порог отбирает 24 февраля 2022 года. А это ровно те наблюдения, ради
которых берутся десять лет истории: «тяжёлые хвосты» распределения, которые
обосновывают переход от параметрического VaR к историческому, и готовые
исторические сценарии стресс-тестирования.

**Задача не в том, чтобы убрать выбросы, а в том, чтобы отличить техническую
аномалию от рыночного события.**

### Алгоритм

Файл `Infrastructure/Services/CorporateActionService.cs`.

Шаг 1. Для каждой пары соседних котировок считается логарифмическая доходность.
Если её модуль не превышает порога 0,40 — идём дальше.

```csharp
private const double AnomalyThreshold = 0.40;
```

Порог 0,40 — это примерно −33 % или +49 % за день.

Шаг 2. Направление изменения определяет вид действия: падение цены —
кандидат на дробление, рост — на консолидацию.

Шаг 3. Наблюдаемое отношение цен сравнивается с коэффициентами, применяемыми
на практике:

```csharp
private static readonly decimal[] KnownRatios =
    [2m, 3m, 4m, 5m, 6m, 8m, 10m, 20m, 50m, 100m, 1000m];
```

Шаг 4. Если отношение совпало с одним из коэффициентов с отклонением не более
5 процентов — это корпоративное действие. Допуск нужен потому, что в день
дробления цена меняется ещё и от торгов: у Норникеля наблюдаемое отношение
вышло 98,42 при коэффициенте 100, то есть отклонение 1,58 процента.

Шаг 5. Не совпало — рыночное событие, корректировка не применяется.

**Результат работы алгоритма на реальных данных:**

```
GMKN   2024-04-08  15054.00 ->  152.96  ln(r)=-4.5892  [Split]
IMOEX  2022-02-24   3084.74 -> 2058.12  ln(r)=-0.4047  [MarketEvent]
ROSN   2022-02-24    431.30 ->  274.70  ln(r)=-0.4511  [MarketEvent]
SBER   2022-02-24    208.53 ->  132.18  ln(r)=-0.4559  [MarketEvent]
```

Для SBER отношение 208,53 / 132,18 = 1,5776 — ближайший коэффициент 2,
отклонение 21 процент, значительно больше допуска. Поэтому рыночное событие.

### Как применяется корректировка

Исходные котировки **не изменяются никогда**. Корректировка применяется при
построении ценового ряда — файл `Infrastructure/Services/PriceSeriesService.cs`.

Правило: все котировки **до** даты корпоративного действия умножаются на
корректирующий множитель. Для дробления 1 к 100 множитель равен 0,01.

Ряд обходится от последней даты к первой с накоплением произведения:

```csharp
for (var i = quotes.Count - 1; i >= 0; i--)
{
    var (date, close) = quotes[i];

    while (adjustmentIndex < adjustments.Count &&
           adjustments[adjustmentIndex].Date > date)
    {
        cumulativeFactor *= adjustments[adjustmentIndex].Factor;
        adjustmentIndex++;
    }

    points[i] = new PricePoint(date, close, close * cumulativeFactor);
}
```

Обход в обратную сторону нужен, чтобы при нескольких дроблениях к ранним
котировкам автоматически применялось произведение всех последующих множителей.
Сложность линейная по длине ряда.

**Проверка на GMKN:**

```
дата          close(биржа)   adjustedClose   ln(r) исх.   ln(r) скорр.
2024-04-01        15054.00        150.5400      -0.0037        -0.0037
2024-04-08          152.96        152.9600      -4.5892        +0.0159   <- дробление
2024-04-09          164.00        164.0000      +0.0697        +0.0697
```

Доходность дня дробления превратилась из −4,5892 в +0,0159. Это реальное
движение цены за период приостановки торгов (со 2 по 5 апреля торги не велись).

### Единственная точка доступа к ценам

Интерфейс `IPriceSeriesProvider` — **единственный** способ, которым расчётная
часть получает цены. Напрямую к таблице `quotes` расчёты не обращаются. Это
гарантирует, что нескорректированные данные в модель не попадут физически.

У него два метода:

- `GetSeriesAsync` — ряд одного инструмента;
- `GetAlignedSeriesAsync` — ряды нескольких инструментов, приведённые к общему
  торговому календарю.

Второй понадобится на этапе расчёта ковариационной матрицы портфеля. Если у
одной бумаги торги приостанавливались, а у другой нет, то без выравнивания
календарей доходности разных торговых дней окажутся сопоставлены друг с другом,
и корреляции будут посчитаны неверно. Метод берёт пересечение дат по всем
инструментам.

### Хранение и ручное переопределение

Все найденные аномалии пишутся в таблицу `corporate_actions`, включая
признанные рыночными событиями. Это документирует, что каждое наблюдение было
проверено, а не пропущено.

Поля:

- `action_type` — Split, ReverseSplit или MarketEvent;
- `ratio` — коэффициент (100 для дробления Норникеля);
- `adjustment_factor` — множитель для более ранних котировок (0,01);
- `observed_ratio`, `observed_log_return` — исходное наблюдение, на основании
  которого принято решение;
- `source` — Automatic или Manual;
- `is_confirmed` — подтверждено ли пользователем;
- `is_applied` — применять ли корректировку;
- `comment` — текстовое обоснование, формируется алгоритмом.

Автоматическая классификация ставит `is_confirmed = false`, но
`is_applied = true` для корпоративных действий: иначе расчёты по умолчанию шли
бы на заведомо испорченных данных. Пользователь может изменить классификацию
методом `PUT /api/corporate-actions/{id}` — запись помечается как внесённая
вручную и при повторных запусках выявления не перезаписывается.

### Известное ограничение: дивидендные разрывы

В день закрытия реестра цена падает примерно на величину дивиденда. Для
российского рынка это единицы процентов — порог 0,40 такое не ловит.

Это **сознательно оставлено** и зафиксировано как ограничение в
[ADR-0007](adr/0007-korporativnye-dejstviya.md). Честно названное ограничение
на защите вопросов не вызывает, а необнаруженная ошибка — вызывает.

### Что спросят на защите

**«Почему вы не удалили выбросы?»** Потому что среди них есть настоящие
рыночные шоки, которые составляют предмет исследования. Задача — отличить
техническую аномалию от рыночного события, а не убрать все крайние значения.

**«Как вы отличаете дробление от падения рынка?»** По совпадению отношения цен
с коэффициентом дробления в пределах допуска 5 процентов. У Норникеля
отношение 98,42 при коэффициенте 100 — совпало. У Сбербанка 1,5776 против
ближайшего коэффициента 2 — отклонение 21 процент, не совпало.

**«Вы меняете исходные данные?»** Нет. Котировки хранятся в том виде, в каком
их опубликовала биржа. Корректировка применяется при построении ряда для
расчёта и полностью обратима.

**«Насколько это вообще важно?»** Без корректировки годовая волатильность GMKN
оценивается в 148,73 процента вместо 31,07 — завышение в 4,79 раза. При этом
расчёт не выдаёт ошибки, результат выглядит правдоподобно.

### Почему логарифмическая доходность

Два определения:

- простая: `r = P(t) / P(t−1) − 1`
- логарифмическая: `r = ln(P(t) / P(t−1))`

У них **разные свойства аддитивности**, и это не теоретическая тонкость.

**Логарифмическая складывается по времени.** Сумма дневных логарифмических
доходностей за период в точности равна логарифмической доходности за весь
период. Отсюда растёт правило корня из времени, по которому дневной VaR
пересчитывается на горизонт в 10 дней.

**Простая складывается по инструментам.** Доходность портфеля равна сумме
доходностей бумаг, взвешенных по долям. У логарифмической такого свойства нет.

Поэтому: расчёты по отдельной бумаге — логарифмическая, агрегирование в
портфель — простая. Оба свойства закреплены тестами:

```csharp
[Fact]
public void Логарифмические_доходности_аддитивны_по_времени()
{
    var returns = ReturnCalculator.Calculate(prices, ReturnType.Logarithmic);
    var sum = returns.Sum(r => r.Value);
    var total = Math.Log(prices[^1].Price / prices[0].Price);
    Assert.Equal(total, sum, Tolerance);       // совпадает
}

[Fact]
public void Простые_доходности_не_аддитивны_по_времени()
{
    // ... Assert.NotEqual — не совпадает
}
```

Второй тест выглядит странно — он проверяет, что что-то **не** работает. Но
именно он документирует, почему сделан такой выбор.

### Две оценки асимметрии и эксцесса

Тонкость, на которой легко попасться. Асимметрию и эксцесс считают двумя
способами:

- **оценки по моментам** `g1`, `g2` — с делителем `n`. Именно они входят в
  статистику Жарка — Бера;
- **скорректированные оценки** `G1`, `G2` — с поправкой на смещение. Это то,
  что выдают функции `СКОС` и `ЭКСЦЕСС` в Excel.

Для эталонной выборки из 8 значений: `g1 = 0,65625`, а `G1 = 0,8185`.
Разница почти на четверть.

Система возвращает **обе**. Если при проверке расчётов в Excel сравнивать не с
той оценкой, получится расхождение, которое выглядит как ошибка в коде. Поля
называются `skewness` / `skewnessAdjusted` и `excessKurtosis` /
`excessKurtosisAdjusted`.

### Критерий Жарка — Бера и зачем он нужен

Это логический стержень всей работы. Цепочка рассуждений такая:

1. Параметрический метод VaR предполагает, что доходности распределены
   нормально. Квантиль считается как `σ · z(α)`.
2. Если предположение неверно, оценка **систематически занижает риск** — потому
   что не учитывает «тяжёлые хвосты».
3. Критерий Жарка — Бера проверяет это предположение.
4. Если гипотеза отвергается — параметрического метода недостаточно, нужны
   исторический метод и Монте-Карло, которые не требуют предположений о виде
   распределения.

Без пункта 3 переход к трём методам выглядит как «сделал побольше методов на
всякий случай». С ним — как обоснованное решение.

Статистика критерия:

```
JB = n / 6 · (S² + K² / 4)
```

где `S` — асимметрия, `K` — эксцесс. При справедливости гипотезы о нормальности
подчиняется распределению хи-квадрат с двумя степенями свободы. Критические
значения: 5,99 при уровне значимости 5 %, 9,21 при 1 %.

В реализации есть приятная проверка: для хи-квадрат с двумя степенями свободы
достигаемый уровень значимости выражается в замкнутом виде `exp(−JB / 2)`.
Тест сверяет результат библиотеки MathNet с этой формулой — так проверяется,
что библиотека вызвана правильно.

### Модульные тесты: как проверена математика

30 тестов. Принцип: эталонные значения получены **независимо от кода** — вручную
или по замкнутым формулам.

Основная эталонная выборка `x = (2; 4; 4; 4; 5; 5; 7; 9)`, все моменты посчитаны
на бумаге и выписаны в комментарии к тестовому классу:

```
среднее                     = 40 / 8 = 5
второй центральный момент   m2 = 32 / 8 = 4
третий центральный момент   m3 = 42 / 8 = 5,25
четвёртый центральный       m4 = 356 / 8 = 44,5
асимметрия                  g1 = 5,25 / 4^1,5 = 0,65625
эксцесс                     g2 = 44,5 / 16 − 3 = −0,21875
JB = 8/6 · (0,65625² + 0,21875²/4) = 0,590169
```

Отдельно стоит отметить два приёма.

**Детерминированная нормальная выборка.** Чтобы проверить, что на нормальных
данных гипотеза не отвергается, нужна нормальная выборка. Генератор случайных
чисел дал бы тест, который иногда падает. Вместо этого значения берутся как
квантили нормального распределения в равноотстоящих точках — результат
полностью воспроизводим.

**Проверка библиотеки замкнутой формой.** Достигаемый уровень значимости от
MathNet сверяется с `exp(−JB / 2)`. Если библиотека вызвана неправильно, тест
это поймает.

При первом запуске один тест упал: эталонное значение `G1` было выписано с
ошибкой в седьмом знаке (`0,818486821` вместо `0,8184875534`). Код был верен,
ошибка была в эталоне. Это как раз то, ради чего тесты и пишутся.

### Что спросят на защите

**«Почему логарифмическая доходность, а не обычная?»** Она аддитивна по
времени, на чём основано правило корня из времени при пересчёте VaR на горизонт
в несколько дней. Для агрегирования в портфель используется простая, так как
она аддитивна по инструментам.

**«Зачем тест на нормальность?»** Он обосновывает выбор методов оценки риска.
Параметрический VaR предполагает нормальность; тест показывает, что
предположение не выполняется, откуда и следует необходимость исторического
метода и Монте-Карло.

**«А может, дело в одном дне 2022 года?»** Нет. На периоде 2016–2021 без этого
дня статистика падает с 929 507 до 7 135, но критическое значение 5,99
превышено всё равно в тысячу с лишним раз.

**«Как вы проверили, что формулы реализованы верно?»** 30 модульных тестов на
эталонной выборке, все моменты которой вычислены вручную и приведены в
комментарии к тесту. Расчётное ядро не зависит от базы данных, поэтому тесты
выполняются за 50 миллисекунд без развёртывания СУБД.

**«Почему у вас две асимметрии?»** Оценка по моментам входит в статистику
Жарка — Бера, скорректированная совпадает с функцией `СКОС` в Excel. Возвращаю
обе, чтобы результаты можно было сверить с табличным процессором.

## Этап 4. VaR тремя методами и CVaR

**Коммит:** `Этап 4: VaR тремя методами, CVaR, разложение Холецкого`

Центральный этап работы. Здесь появляется то, ради чего всё строилось.

### Что сделано

Три метода оценки стоимостной меры риска, ожидаемые потери, разложение

### Соглашение о знаке

Важная деталь, из-за которой легко запутаться. **VaR возвращается как
положительное число, означающее потерю.**

Доходность в «хвосте» отрицательна: квантиль уровня 1 % для SBER равен
−5,7 %. Стоимостная мера риска — это величина потери, поэтому берётся
с обратным знаком: `VaR = −q = 5,7 %`. В рублях при позиции в миллион —
57 003 рубля.

Читается так: «с вероятностью 99 % потери за торговый день не превысят
57 003 рубля».

### Параметрический метод

```
q(1−α) = μ + z(1−α) · σ
VaR(α) = −(μ + z(1−α) · σ) · V
```

где `z(1−α)` — квантиль стандартного нормального распределения. Для уровня
доверия 99 % он равен −2,3263.

Ожидаемые потери при нормальном распределении выражаются в замкнутом виде:

```
ES(α) = (−μ + σ · φ(Φ⁻¹(α)) / (1 − α)) · V
```

Для 99 % множитель равен 2,6652 против 2,3263 у квантиля — ожидаемые потери
всегда больше VaR, потому что усредняют весь «хвост», а не его границу.

Оба значения проверены тестами с точностью до десятого знака.

### Метод исторического моделирования

Никаких предположений о распределении. Оценкой квантиля служит выборочный
квантиль фактически наблюдавшихся доходностей, ожидаемые потери — среднее по
наблюдениям ниже этого квантиля.

Ограничение, которое стоит помнить: при 2513 наблюдениях уровню доверия 99 %
соответствуют всего **25 наблюдений в хвосте**. Оценка получается шумной.

### Метод Монте-Карло и разложение Холецкого

Это место, которое спросят на защите обязательно.

**Задача.** Доходности бумаг в портфеле не независимы: при падении рынка
дешевеет всё сразу. Если моделировать их независимо, портфель получит мнимую
диверсификацию, и риск окажется занижен.

**Решение.** Нужны случайные векторы с заданной ковариационной матрицей Σ.
Разложение Холецкого представляет симметричную положительно определённую
матрицу в виде

```
Σ = L · Lᵀ,     L — нижняя треугольная
```

Если `z` — вектор независимых стандартных величин (то есть `E[z·zᵀ] = I`), то

```
E[(L·z)(L·z)ᵀ] = L · E[z·zᵀ] · Lᵀ = L · I · Lᵀ = L · Lᵀ = Σ
```

То есть вектор `L · z` имеет ровно ту ковариационную матрицу, которая нужна.
Три строчки выкладок — и это весь фокус.

В коде умножение использует треугольность матрицы:

```csharp
for (var i = 0; i < assetCount; i++)
{
    double sum = 0.0;
    for (var j = 0; j <= i; j++)      // только до i: матрица нижняя треугольная
    {
        sum += factor[i, j] * independent[j];
    }
    shocks[i] = sum;
}
```

Доходность инструмента в сценарии на горизонте `h`:

```
r(i) = μ(i) · h + √h · (L · z)(i)
```

А доходность портфеля считается через **простые** доходности, потому что
именно они аддитивны по составу:

```
R = Σ w(i) · (exp(r(i)) − 1)
```

Вот здесь и пригодилось различие простой и логарифмической доходности из
этапа 3.

**Если матрица вырождена.** При линейно зависимых рядах доходностей разложение
Холецкого невозможно. Код перехватывает это и добавляет малую величину к
главной диагонали — приём регуляризации, который восстанавливает положительную
определённость, практически не меняя оценок.

### Три закона распределения в Монте-Карло

| Закон | Зачем |
| --- | --- |
| Нормальный | Проверка корректности: оценка обязана сойтись к параметрической |
| Стьюдента | Воспроизводит «тяжёлые хвосты»; ν оценивается по эксцессу как `4 + 6/g₂` |
| Историческая бутстрэп-выборка | Ни одного предположения: берутся реальные дни целиком |

Про бутстрэп стоит сказать отдельно: на каждый день горизонта случайно
выбирается один из реально наблюдавшихся торговых дней, и берутся доходности
**всех** бумаг за этот день. Взаимосвязи сохраняются сами собой, без
ковариационной матрицы и без разложения Холецкого.

Для распределения Стьюдента есть тонкость: его дисперсия равна `ν/(ν−2)`, а не
единице. Чтобы сравнение с нормальным было честным, величина делится на
`√(ν/(ν−2))` — тогда дисперсия совпадает, а отличаются только хвосты.

### Воспроизводимость

Генератор — Mersenne Twister с задаваемым начальным значением. Два запуска с
одинаковыми параметрами дают побитово одинаковый результат; это закреплено
тестом. Без этого нельзя было бы кэшировать расчёты и сверять результаты
(см. ADR-0005).

### Тест, который оказался неправ

При первом прогоне упал тест «исторический метод учитывает тяжёлые хвосты».
Разбор показал, что ошибка была в **тесте**, а не в коде.

Конструкция была такая: 1000 наблюдений ±0,5 %, из них ровно 10 заменены
на −15 %. Ожидалось, что исторический VaR окажется выше параметрического.
Фактически:

```
параметрический VaR = 0,03812
исторический   VaR = 0,00645
```

Причина: доля выбросов ровно 1 %, то есть в точности равна уровню 1 − α.
Квантиль 1 % попадает **на границу** между −0,15 и −0,005 и при интерполяции
почти полностью «садится» на тело распределения. При этом те же десять
выбросов раздувают σ примерно в десять раз, и параметрическая оценка
взлетает.

Вывод: утверждение «исторический VaR выше параметрического» **не является
общим правилом**. Оно зависит от того, как масса хвоста расположена
относительно уровня доверия — ровно то, что потом и подтвердилось на реальных
данных переломом около 98 %.

Тест переписан в два: один на асимметричном распределении с долей хвоста 3 %
(там исторический действительно выше), второй — на исходной конструкции,
где выше параметрический. Второй теперь прямо документирует, что общего
правила нет.

### Что спросят на защите

**«Зачем три метода, если можно один?»** Сопоставление методов и есть
содержательный результат: оно количественно показывает, во сколько раз
предположение о нормальности искажает оценку. При 99 % занижение ожидаемых
потерь достигает 1,7 раза.

**«Что такое разложение Холецкого и зачем оно?»** Способ получить случайные
векторы с заданной ковариационной матрицей. `Σ = L·Lᵀ`, и если `z`
независимы, то `L·z` имеет ковариационную матрицу Σ. Без него доходности
бумаг моделировались бы независимо, и риск портфеля оказался бы занижен за
счёт мнимой диверсификации.

**«Как вы убедились, что Монте-Карло работает правильно?»** При нормальном
законе распределения он обязан сойтись к аналитической параметрической
оценке. Сошёлся: 4,820 % против 4,910 %, расхождение 1,8 %. Это закреплено
тестом с допуском 3 %.

**«Почему CVaR, а не только VaR?»** VaR указывает границу потерь, но ничего
не говорит об их величине при её превышении. CVaR усредняет весь хвост.
Базельский комитет в стандарте FRTB заменил VaR на CVaR именно по этой
причине. На наших данных разница между методами по CVaR втрое больше, чем
по VaR.

**«Почему на 95 % параметрический метод завышает риск?»** Потому что
фактическое распределение острее нормального в центральной области: за
пределами двух сигм наблюдений меньше, чем предсказывает нормальный закон.
Занижение начинается только с уровня около 98,2 %.

### Проверка согласованности расчёта

Доля систематического риска считается двумя независимыми путями:

1. через разложение дисперсии: `β²·σ²(рынка) / σ²(инструмента)`;
2. как коэффициент детерминации регрессии `R²`.

Математически это одна и та же величина. Тест проверяет их совпадение с
точностью 1e-9 — если в одном из расчётов ошибка, тест это поймает.

### Диверсификация в цифрах

Корреляционная матрица пяти акций, 2509 наблюдений общего календаря:

|  | SBER | GAZP | LKOH | GMKN | ROSN |
| --- | ---: | ---: | ---: | ---: | ---: |
| **SBER** | 1,000 | 0,570 | 0,554 | 0,483 | 0,629 |
| **GAZP** | 0,570 | 1,000 | 0,556 | 0,478 | 0,595 |
| **LKOH** | 0,554 | 0,556 | 1,000 | 0,479 | **0,706** |
| **GMKN** | 0,483 | 0,478 | 0,479 | 1,000 | 0,495 |
| **ROSN** | 0,629 | 0,595 | 0,706 | 0,495 | 1,000 |

Средняя парная корреляция **0,554**. Наибольшая — LKOH и ROSN (0,706), обе
нефтяные. Наименьшая — GMKN с остальными (0,478–0,495), металлургия слабее
связана с нефтегазом.

Эффект диверсификации:

```
средневзвешенная волатильность составляющих : 33,17 %
волатильность равновзвешенного портфеля     : 26,65 %
снижение риска                              : 19,7 %
```

Средневзвешенная волатильность — это то, что получилось бы при корреляции,
равной единице. Разница и есть вклад диверсификации.

Считается через квадратичную форму `σ² = wᵀ·Σ·w` — та же ковариационная
матрица, что используется в разложении Холецкого на этапе 4.

### Второй тест, оказавшийся неправым

При первом прогоне упал тест «коэффициент Сортино ниже коэффициента Шарпа при
отрицательной асимметрии». Разбор дал неожиданный результат.

Сначала выяснилось, что в моей выборке среднее было **отрицательным**, а при
отрицательной избыточной доходности знак неравенства переворачивается. Но
попытки построить корректную выборку не удались — и оказалось, что это
невозможно **в принципе**.

Пусть `X = r − MAR`. Тогда:

```
σ²  = E[X²] − (E[X])²
DD² = E[X² · 1{X<0}]
```

откуда

```
DD² = σ² + (E[X])² − E[X² · 1{X>0}]
```

По неравенству Коши — Буняковского `(E[X])² ≤ (E[X·1{X>0}])² ≤ E[X²·1{X>0}]`,
следовательно **DD² ≤ σ²** всегда.

Вывод: при принятом определении отклонения вниз (знаменатель — общее число
наблюдений) **коэффициент Сортино не может быть ниже коэффициента Шарпа, пока
избыточная доходность положительна**. Распространённое утверждение «Сортино
ниже Шарпа — значит отрицательная асимметрия» для этого определения неверно.

Исправлено два места: текст вывода в расчётчике (теперь характеризует
величину превышения, а не его знак) и сам тест, который теперь проверяет
доказанное неравенство, в том числе на отрицательно асимметричной выборке.

Это пример того, как модульный тест выявил не ошибку в коде, а ошибку
в понимании модели. Такое на защите звучит гораздо лучше, чем «всё работало
с первого раза».

### Что спросят на защите

**«Почему все коэффициенты Шарпа отрицательные?»** За период 2016–2026
доходность акций (0,12–6,38 % годовых) оказалась ниже средней ключевой ставки
Банка России (10,56 %). Период включает 2022 год и длительные периоды высокой
ставки. Кроме того, доходность считается по ценовому ряду без учёта
дивидендов, что занижает полную доходность вложения.

**«Почему безрисковая ставка именно ключевая?»** Это официальный ориентир
стоимости денег в рублях, публикуемый Банком России ежедневно. Альтернатива —
доходность ОФЗ — потребовала бы выбора конкретного выпуска и учёта срока
до погашения.

**«У SBER альфа 5 % годовых — значит, бумага обыгрывает рынок?»** Нет.
t-статистика альфы 0,74 при критическом значении 1,96: значение статистически
неотличимо от нуля. Ни по одной из пяти бумаг значимой альфы не обнаружено.

**«Зачем считать долю систематического риска двумя способами?»** Разложение
дисперсии и коэффициент детерминации математически должны совпадать. Их
сверка — способ проверить корректность реализации, закреплённый тестом.

**«Что даёт диверсификация количественно?»** Равновзвешенный портфель из пяти
акций имеет волатильность 26,65 % против 33,17 % средневзвешенной по
составляющим — снижение риска на 19,7 % при средней парной корреляции 0,554.

### Компонентный VaR: кто на самом деле создаёт риск

Главная новая вещь этапа. Задача формулируется так: риск портфеля меньше
суммы рисков позиций, и непонятно, какую часть общего риска создаёт каждая.

**Разложение Эйлера.** VaR — однородная функция первой степени от вектора
долей: увеличили все позиции вдвое — риск вырос вдвое. Для таких функций
работает тождество Эйлера:

```
VaR(w) = Σ w(i) · ∂VaR / ∂w(i)
```

Слагаемые справа — компонентные меры риска. Их сумма **в точности** равна
риску портфеля, поэтому общий риск распределяется между позициями
однозначно.

Производная берётся аналитически. Волатильность портфеля `σ(p) = √(wᵀ·Σ·w)`,
откуда `∂σ(p)/∂w(i) = (Σ·w)(i) / σ(p)`, и

```
∂VaR / ∂w(i) = −z(1−α) · √h · (Σ·w)(i) / σ(p) − μ(i) · h
```

В коде это одна строка на элемент — произведение строки ковариационной
матрицы на вектор долей:

```csharp
double covarianceWithPortfolio = 0.0;
for (var j = 0; j < count; j++)
{
    covarianceWithPortfolio += covariance[i, j] * weights[j];
}
```

**Для ожидаемых потерь** разложение записывается вообще без
дифференцирования:

```
ES(p) = Σ w(i) · E[ r(i) | r(p) ≤ q ]
```

То есть: берём сценарии, где портфель в «хвосте», и смотрим среднюю
доходность каждой бумаги именно в этих сценариях. Тождество выполняется
точно по построению — доходность портфеля в каждом сценарии и есть
взвешенная сумма.

### Результат на модельном портфеле

Портфель из пяти голубых фишек, текущая стоимость 4 162 120 рублей
(вложено 5 017 500, результат −17,0 %). Уровень доверия 99 %, горизонт
один день:

| Метод | VaR, руб. | CVaR, руб. |
| --- | ---: | ---: |
| Параметрический | 161 950 | 185 601 |
| Историческое моделирование | 168 094 | **300 950** |
| Монте-Карло, нормальное | 159 131 | 182 468 |
| Монте-Карло, бутстрэп | 167 605 | 294 054 |

Та же картина, что на отдельных бумагах: по CVaR параметрический метод
занижает в 1,6 раза.

**Разложение риска:**

| Тикер | Доля | Вклад в риск | Компонентный VaR | Обособленный VaR | Выигрыш дивер. |
| --- | ---: | ---: | ---: | ---: | ---: |
| SBER | 24,3 % | **25,5 %** | 41 261 | 49 671 | 8 410 |
| GAZP | 19,3 % | 20,8 % | 33 713 | 42 014 | 8 301 |
| ROSN | 17,3 % | 18,9 % | 30 552 | 36 237 | 5 686 |
| LKOH | 18,9 % | 17,8 % | 28 825 | 35 810 | 6 985 |
| GMKN | 20,2 % | **17,0 %** | 27 600 | 38 164 | **10 564** |
| **Итого** | 100 % | 100 % | **161 950** | 201 895 | 39 945 |

Смотри на строки SBER и GMKN. У GMKN **доля меньше** (20,2 % против 24,3 %),
а вклад в риск **ещё меньше** (17,0 % против 25,5 %). Почему: по данным
этапа 5 Норникель слабее связан с остальными бумагами портфеля (парные
корреляции 0,478–0,495 против 0,554–0,706). Поэтому он даёт наибольший
выигрыш от диверсификации — 10 564 рубля.

Практический вывод, который и есть смысл всей затеи: **чтобы снизить риск
портфеля, сокращать надо не самую большую позицию, а ту, у которой
наибольший вклад в риск.** Здесь это SBER.

### Тождество Эйлера разошлось — и это была моя ошибка

При первом прогоне на реальных данных проверка дала:

```
сумма компонент  161 949,92
VaR портфеля     161 054,40
расхождение      0,56 %
```

Модульные тесты при этом проходили. Причина: в тестах я строил
параметрический VaR по тем же средним, что использует разложение,
а в реальном коде — по разным.

В `PortfolioRiskCalculator` средняя доходность портфеля бралась как среднее
по ряду **простых** доходностей портфеля, а среднеквадратическое отклонение
и разложение — по ковариационной матрице **логарифмических** доходностей.
Смешение двух основ и дало расхождение.

Исправлено приведением к единой основе: средняя доходность портфеля теперь
считается как взвешенная сумма средних логарифмических доходностей
инструментов. Расхождение стало 5,8·10⁻¹¹ — машинная точность.

Дополнительно в расчёт встроена проверка: если тождество нарушено более чем
на 10⁻⁹ относительной величины, расчёт прерывается с ошибкой. Теперь такое
рассогласование не пройдёт молча при будущих правках.

Урок общий: модульный тест проверяет то, что в нём написано. Если в тесте
данные готовятся не так, как в рабочем коде, тест пройдёт при сломанном
коде. Проверка инварианта **внутри** расчёта надёжнее.

### Асинхронные расчёты

Расчёт на 500 000 сценариев с горизонтом 10 дней занимает около 1,9 секунды.
Держать HTTP-соединение всё это время нельзя, поэтому схема такая:

```
POST /api/portfolios/1/calculations
  -> запись в risk_calculations, статус Queued, параметры в jsonb
  -> идентификатор в очередь
  <- 202 Accepted, Location: /api/calculations/{id}

фоновая служба: Queued -> Running -> Succeeded, результат в jsonb

GET /api/calculations/{id}
  <- статус, а после завершения — результат
```

Проверено вживую: `Queued → Running (7 опросов) → Succeeded`, 1859 мс,
результат сохранён и прочитан.

**Почему не Hangfire.** Он даёт готовую очередь с сохранением в базе и
панель наблюдения, но требует своего набора таблиц и внешней зависимости.
Состояние расчётов и так хранится в `risk_calculations` — хранить очередь
во втором месте означало бы дублирование. Стандартный `Channel<Guid>` плюс
`BackgroundService` решают задачу примерно в ста строках.

Две детали реализации, о которых стоит знать:

- **Канал ограничен по длине** (256). При заполнении постановка нового
  расчёта ждёт освобождения места — иначе при массовой постановке память
  росла бы неограниченно.
- **Своя область внедрения зависимостей на каждый расчёт.** Контекст базы
  данных зарегистрирован как scoped и не может использоваться фоновой
  службой напрямую — она живёт всё время работы приложения. Поэтому
  `_scopeFactory.CreateScope()` на каждую задачу.

Известное ограничение: очередь в памяти процесса. При перезапуске приложения
записи со статусом `Queued` не возобновляются. Зафиксировано в ADR-0010.

На горизонте 10 дней методы разошлись сильнее, чем на однодневном:

| Метод | VaR, руб. |
| --- | ---: |
| Монте-Карло, нормальное | 477 225 |
| Параметрический | 509 297 |
| Историческое моделирование | 531 561 |
| Монте-Карло, бутстрэп | **558 721** |

Разрыв между параметрическим методом и Монте-Карло по нормальному закону

### Что спросят на защите

**«Как вы определили, какая позиция создаёт риск?»** Разложением Эйлера.
VaR однороден первой степени по долям, поэтому сумма произведений доли
на частную производную в точности равна VaR портфеля. Это даёт однозначное
распределение риска между позициями.

**«Чем компонентный VaR отличается от обособленного?»** Обособленный — это
риск позиции, взятой отдельно; их сумма превышает риск портфеля.
Компонентный учитывает корреляцию с остальным портфелем, и их сумма равна
риску портфеля точно. Разность и есть выигрыш от диверсификации.

**«Почему у Норникеля доля 20 %, а вклад в риск 17 %?»** Потому что он
слабее коррелирован с остальными бумагами портфеля — парные корреляции
0,478–0,495 против 0,554–0,706 у прочих. Он даёт наибольший выигрыш
от диверсификации.

**«Как вы проверяете, что разложение верно?»** Тождеством Эйлера: сумма
компонентных мер обязана равняться мере риска портфеля. Проверка встроена
в расчёт и прерывает его при расхождении свыше 10⁻⁹. Фактическое
расхождение — 5,8·10⁻¹¹.

**«Почему расчёт асинхронный?»** Монте-Карло на 500 тысячах сценариев
занимает около двух секунд, и при росте портфеля — больше. Запрос
принимается, ставится в очередь и выполняется фоновой службой; клиент
получает код 202 и забирает результат по идентификатору.
